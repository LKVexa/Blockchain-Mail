# Direct Internet email

The protected workspace has one mailbox interface for local and Internet email. Start the workspace normally, unlock it, and open your mailbox. On first login, the server checks the signed address register and assigns an available address such as `rmail@127.0.0.2`. This reservation persists across restarts. If your mailbox already has a canonical 127 address, login reuses it. Choose **New message**, enter the recipient, and press **Send**. The address determines delivery automatically: local addresses use the local mailbox, and public domains use recipients' DNS MX servers. There is no delivery-mode or interface selection. No message is sent on login or configuration changes.

The root page and previously saved `/mail/`, `/internet/`, and `/desk/index.html` links all open this same interface. Inbox and Sent belong to the authenticated account. Sent combines local sent messages with that account's Internet delivery results. The assigned address is used in local message headers as well as the default Internet sender. Settings includes an Internet sending enable/pause control, preserving any saved sender configuration.

Your assigned address is displayed after connecting and becomes the enabled sender automatically, with a matching bracketed SMTP greeting such as `[127.0.0.2]`. You do not need to create or type a local domain or save sender settings before sending. Every authenticated mailbox can use Internet email. Its settings and send history belong to that account; ordinary users cannot send as another account. Operators may choose a custom sender for their own account. Explicit personal settings are preserved across logins and restarts.

Allocation reserves `127.0.0.1` for the service and selects an unused host from `127.0.0.2` through `127.0.0.254`, checking both mailbox and alias claims. The new address points to your existing local Inbox and keeps your existing credentials and credits. The reservation and ownership record are committed in the same signed transaction. Repeated login does not allocate another address or add another assignment block. Existing 127 game mailboxes keep their identity; older game mailboxes can receive through their own assigned address. The register is exclusive within this workspace's signed chain.

A local sender can attempt delivery; the remote server decides whether to accept it. Local sender addresses are not publicly reachable for replies or returned delivery failures. Assigned puzzle-owner mailboxes can use ordinary signed local credit postage through the shared form, subject to their balance, daily limit, consent, and storage quota. This does not mint credits or consume a puzzle permit. Retained puzzle APIs preserve their game-bound message and postage rules.

The client resolves the recipient domain's MX records, tries mail exchanges in preference order, resolves and pins public destination IP addresses, then connects to SMTP port 25. A domain with no MX data can use its own A/AAAA records; a null MX or nonexistent domain is refused. Connections to private, loopback, link-local and reserved destination addresses are refused. STARTTLS with a valid certificate is required before sending the envelope or body. General application DNS, outgoing TCP, UDP, child execution and public listeners retain the previous runtime guard; the outgoing mail capability alone owns its DNS and SMTP sockets.

The machine's network must permit outgoing TCP port 25. Recipient policies may reject local sender domains, residential IP addresses, missing SPF, missing reverse DNS, or other authentication and reputation issues. For reliable public delivery, configure a domain you control, authorize the sending public IP in SPF, and arrange matching forward/reverse DNS. This build does not generate DKIM signatures, receive Internet mail, manage a public domain's DNS records, process remote bounces, or prove recipient Inbox placement. Sender-domain MX records are needed for receiving replies and bounces; adding an MX record alone does not enable outgoing SMTP.

Xfinity publishes a block on SMTP port 25 for both IPv4 and IPv6. On October 12, 2026, recipient MX lookups succeeded, but greeting-only TCP checks to Google and Microsoft mail servers timed out; an HTTPS control connected successfully. These checks sent no SMTP commands or messages. This is consistent with Xfinity's documented restriction and prevents direct MX delivery from that connection. Direct sending needs an egress server or network that permits port 25. Authenticated submission through a provider uses a separate service, usually port 587; changing the recipient MX port does not turn it into that service. See [Xfinity's blocked ports](https://www.xfinity.com/support/articles/list-of-blocked-ports) and [Xfinity's port 25 policy](https://www.xfinity.com/support/articles/email-port-25-no-longer-supported).

New delivery attempts distinguish TCP connection timeouts from SMTP greeting, TLS, and command timeouts. They keep a bounded overall deadline, alternate available IPv4 and IPv6 destinations, and retain validated public addresses when one family's DNS lookup is temporarily unavailable. Any DNS answer containing a private or reserved destination is still refused. A failed connection reports SMTP port 25 and the need to check outbound network access. Existing saved attempts retain their original result; they are never silently rewritten or resent.

Messages and personal configuration are stored inside the existing encrypted, signed vault state. The combined outbox is limited to 100 messages and 2 MiB of logical message content, with a 128 KiB body limit per message. Internet mail requires authenticated mailbox access, supports one recipient per message, and uses plain UTF-8 text without attachments. Each account sees only its own outbox. Plaintext compatibility mode cannot use Internet email. Internet sends do not consume local credits or puzzle permits.

Each explicit submission freezes the message, sender, SMTP greeting, stable Message-ID, date and request ID before connecting. The same request ID cannot submit a second message or changed content. Queue and sending transitions are committed before SMTP; later results are committed independently. SMTP and the local database cannot share one atomic transaction.

- **ACCEPTED** means a remote server returned positive acceptance after the message body. It does not prove delivery to the recipient's Inbox.
- **FAILED** means this attempt did not confirm acceptance, such as a DNS/TLS/connect failure or an explicit SMTP rejection. Read the result before starting a new message.
- **UNKNOWN** means the connection or process ended at a point where remote acceptance cannot be ruled out. Check with the recipient before starting a new message.
- **QUEUED / SENDING** indicate an attempt still in progress. After a process interruption, a queued message becomes failed; a sending message becomes unknown. Restart never automatically resends it.

The compose form retains the request ID when a browser request fails and can check the saved attempt. Choosing **New message** creates a new request ID and requires another explicit send. This prevents silent retries while preserving a reviewable record of uncertain delivery. Local and Internet recipients currently need separate messages; an Internet message supports one recipient and plain text only.

The native console now preserves the interface after recoverable browser subprocess notifications. Fatal browser/main-renderer exits still show the retry page. Repeated renderer unresponsiveness gets a bounded recovery grace period. Privacy-limited rotating diagnostics in `console/workspace/logs/console-diagnostics.jsonl` record failure categories and numeric codes without mail content, credentials, or full URLs. The earlier generic failure screen did not retain enough information to prove its historical trigger.
